## 🛠️ Forge parts and why not native

| Forge part | Why not native |
|---|---|
| `forge.mjs worktree` names | A VS Code worktree branch starts with `agents/`, and `create_session` has no branch name or base (microsoft/vscode#321685). Forge needs `repo.branchPattern`. |
| `git branch -m` in a New Worktree session | The same reason. After the rename, **Mark as Done** leaves the worktree (click-check 3), so close checks `git worktree list`. |
| `isolate_session` is not the default | It makes a native worktree, but Forge cannot set its folder or branch name. Click-check 2. |
| Gate approvals with SHA-256 manifests | A native plan approval does not cover a set of exact revisions. |
| Summary budget, `forge.mjs diff`, and the reading levels of older tickets | No native "changed since your last review" exists for wiki files, and no native check keeps a document short. |
| `forge.mjs canvas` and `canvas.html` | A native canvas comes from a canvas extension, runs only in a Copilot harness session, and cannot open without a session ([Canvases](https://code.visualstudio.com/docs/agents/run/canvases)). The docs give no file format for a canvas extension, and an enterprise policy can block one (`strictPluginOnlyCustomization`). The Markdown preview shows one static Mermaid diagram for each file. Forge needs the same page in each host and outside a session, so the page is one generated HTML file without a network request, opened in the integrated browser or in any browser. The first Forge canvas was a canvas extension, and Forge 5.0 removed it because the feature was not reliable. It is a view like `raw/board.md`: no manifest lists it. Forge 7.5 adds the tiers, the views, and the title strips to this page. The editor can fold a Markdown section, and the integrated browser can zoom a page, but no native feature knows which section the user must read for a gate (the integrated browser page, read on 2026-11-18). |
| `forge.mjs canvas <KEY> --serve` and **Send to agent** | Until 7.0 the comments went back by copy and paste, and there was no server. The native **Add Element to Chat** with a comment exists only in the VS Code integrated browser. It sends one page element, without the ticket file and the section, and Claude Code and Copilot CLI have no such tool. A page from a `file://` link cannot give data to a session, and its clipboard permission is not sure (click-check 17). So the command runs a server from the Node standard library on `127.0.0.1` only, for one ticket, with a new token for each run. It starts only with `--serve`, and it stops after the Send, at a stop signal, or after 8 hours. The page sends the comments only to this server, and the command prints them for the session. The `file://` page with **Copy all** stays. The method follows Plannotator (a local server, a send button, the feedback on standard output). |
| Cold read (`agents` skill) | No host checks a document with a reader that does not have the session context. The check uses the native subagent tool, with a prompt that holds only the path of the document. It follows the Elephant-Goldfish pattern (Dave Rensin, Google Research), reduced to one read for each review revision. |
| `forge.mjs board`, `raw/board.md`, and the board page `raw/board.html` | The sessions list and the inbox mode show sessions, not ticket state from the wiki: the gates, the next step, and the waits. The Markdown preview of `board.md` has no filter, and its links open Markdown files. So Forge 7.2 adds the same data as one HTML page, with the same limits as the ticket canvas: one file, no network request, never a source. Forge removed its first canvas in 5.0: it was a Copilot canvas extension, and that feature was not reliable then. |
| `forge.mjs live`, `scripts/live-hook.mjs`, the live line of the board, and the Live panel of the canvas | Each host has a native view of its own sessions: the agent view of Claude Code (`claude agents`), the agent list of Orca, and the sessions list and the inbox mode of VS Code. None shows a session next to the gates, the next step, and the waits of its ticket. The transcript files of Claude Code are an internal format ([Sessions](https://code.claude.com/docs/en/sessions)), and a copy of a terminal has no subagent structure and needs a PTY module. So Forge 7.6 uses the native hooks: a background hook sends one small event to a server from the Node standard library on `127.0.0.1` only. The server is read-only for a session, keeps the events in memory, and starts only with `forge.mjs live`. Forge starts no session and has no terminal: a session runs in Orca, in a terminal, or in the Agents window, as before. |
| Links between the pages: the ticket switcher, the previous and the next ticket, and `/board` and `/ticket/<folder>/` on the canvas server | [Manage sessions](https://code.visualstudio.com/docs/agents/run/sessions/manage-sessions) gives no link (URI) and no command that opens one session from outside (read on 2026-11-17), so a page cannot open the session of a ticket. The favorites, the history, and the tab list of the integrated browser know only pages that the user opened before, not the tickets of the wiki. So each page has relative links to the other pages, and `forge.mjs board` and `forge.mjs canvas <KEY>` write the pages that the links need. A served page of another ticket cannot send comments: the server stops and wakes only the session of its own ticket. A board card has a **Worktree** link (`vscode://file/<folder>`) as the nearest native step to the session (click-check 24). |
| The design system `scripts/lib/ui.mjs` and [design-system.md](design-system.md) | A local HTML page has no native component set, and the docs of the integrated browser name no theme variables for a page. The page must also be the same in Claude Code, in Copilot CLI, and in a plain browser. So the two pages share their own tokens (color, type, space, radius, shadow), a light and a dark theme, and the same bar, switcher, help dialog, and toast. |
| The wiki page (`scripts/lib/wiki.mjs`, `scripts/lib/wiki-page.mjs`, `raw/wiki.html`) | The [Markdown preview](https://code.visualstudio.com/docs/languages/markdown) shows one file inside the VS Code window, and **Find All References** lists the links to a header in the editor (read on 2026-11-18). That page names no index of all Markdown files as one view, no list of the tickets that name a page, and no preview outside VS Code. The board and the canvas are browser pages that also run with Claude Code, Copilot CLI, and Orca. So Forge writes one page with each wiki page, the uses of each page, and the closed tickets, in the same design system. **Open the file** on a page still opens the Markdown file in the editor. |
| The Mermaid file `vendor/mermaid/mermaid.tiny.js` and `scripts/lib/mermaid.mjs` | The Markdown preview of VS Code draws no page outside the VS Code window (see the row above), and a browser has no Mermaid function of its own. A drawing needs the Mermaid library, and a page of Forge loads nothing from a network. So the plugin holds one file of the package `@mermaid-js/tiny` 12.3.0 (MIT, 2.7 MB), with its hash in the code and in a test. The wiki page and the ticket canvas load it from the folder `raw/` or from their own server, and only when the page has a Mermaid block. The user chose this build on 2026-11-18, before the full build (5.3 MB) and before a drawer of Forge for flowcharts only. |
| `forge.mjs open`, and a live server for each repository | The [plugin reference](https://code.claude.com/docs/en/plugins-reference) of Claude Code (read on 2026-11-19) gives a plugin a `bin/` folder, but its files are on the `PATH` of the Bash tool of the agent only, and claude.ai does not install a plugin that has this folder. No host gives a plugin a command for the terminal of the user, and no host shows the tickets and the wiki of a repository as pages. So `open` is a command of `forge.mjs`: it starts the server as a process of its own, and a second run gives the same links. One server for each repository keeps the pages and the sessions of two repositories apart. |
| The Forge folder `../<repo>.forge`, its launcher (`scripts/lib/launcher.mjs`), and `forge.mjs init` and `move` | No host gives a plugin a folder for the data of one repository that the user and each host share: `${CLAUDE_PLUGIN_DATA}` of Claude Code is one folder for a plugin and a user, in the Claude folder (plugin reference, read on 2026-11-19). `${CLAUDE_PLUGIN_ROOT}` "changes when the plugin updates", so a fixed command with the plugin path stops to work at each update. So the Forge folder is next to the repository, and its launcher reads the plugin path from the file `.plugin`, which setup and the `sessionStart` hook write. The wiki is a subfolder with its own git repository, so `raw/` and `archive/` need no `.gitignore` line to stay local. |
| Sync notes in `raw/sync/` | No native cache of tracker, change request, and CI status exists. |
| Title rule: rename first, then again at the end of the first turn | An automatic title can replace a title that was set (microsoft/vscode#338122). |
| Rules in the `sessionStart` hook context, not in `com.github.copilot/rules/` | Plugin rule files loaded in some sessions only (click-check 11). The docs give no always-on format for plugin rules. `COPILOT_CUSTOM_INSTRUCTIONS_DIRS` is global for all repositories, and the CLI does not read `chat.instructionsFilesLocations`. The hook runs in each session, also in `create_session` and custom agent sessions. |
| Company rules in `<wiki>/rules/` with hash trust | The native `AGENTS.md` and `.github/instructions` must be in the workspace. The wiki is a sibling folder, and the code checkout must not change for Forge. A Git pull cannot approve its own rules. |
| Profile config templates in the plugin | A plugin cannot ship workspace settings for one repository. The wiki keeps the copy, so the hash trust and the personal values stay per user. |
| Core and profile overlay (`templates/profile.json`, `templates/profile.md`, `tests/profile.test.mjs`) | No host has a native "company layer" for a plugin. The profile stays an overlay in the same folder: `templates/` and the files that `profile.json` lists. The wiki copies and the trusted rule pages name plugin paths, so a moved folder breaks them. The test keeps the terms of a profile out of all other files. Forge 6.8 renames the sync note field `jira` to `tracker`; the board still reads an old `jira` field. |
| `doctor` MCP check | No native view compares the MCP servers of the profile (`profile.json`) across the plugin, workspace, and user MCP files. `doctor` names each missing server, each server with two entries (the same tools two times in the context), and each retired URL. A profile without servers has no MCP check. |
| Host verbs (`host.title`, `host.spawn`, ...) and the tables in `hosts/` | Agent Plugins 1.0 makes only skills and MCP servers portable. Each host has other session tools (VS Code `rename_chat`, Claude Code `/rename`, Copilot CLI `/rename`), and no standard names them. The hook adds only the table of the current host, so the context does not grow with each host. `host.open` runs `code -r` only in VS Code; the terminal hosts give links, because VS Code can be missing. A test keeps the VS Code tool names out of the portable text. |
| `board` skill, no custom agent | A custom agent file is host specific, and VS Code ignores the body of a plugin agent (click-checks 9 and 14). A skill is portable and runs in any session, so Forge 6.6 has no custom agent. The "no code edits" limit of the board is a written rule. |
| Hand-written manifests and `tests/packaging.test.mjs`, no generator | One plugin folder serves each host: VS Code finds the Agent Plugins `$schema` in the root `plugin.json` first, so `hooks/hooks.json` (Claude Code) does not change it. [rulesync](https://github.com/dyoshikawa/rulesync) writes project config, not plugin folders: it makes no manifest, marketplace, or plugin hook for Copilot, Codex, or pi, and it adds about 23 MB. Agent Plugins 1.0 has no portable hook file. The test keeps the 3 manifests the same and runs each hook command. Add a generator only when two hosts need the same path with different content (Gemini CLI and Claude Code both read `hooks/hooks.json`), or when Agent Plugins 1.1 gives a portable `hooks.json`. |
| Gate guard (`scripts/lib/guard.mjs`, `policy.gateGuard`) | Forge 7.4, writes: the prompt is native, and Forge uses it as the Sendable? "yes" in place of its own manifest and sidecar. A native `ask` rule (for example `Bash(gh issue comment *)`) asks also outside a ticket, cannot name the draft, and a user setting can remove it, so the hook asks. Claude Code accepts a hook `ask` with no prompt in `bypassPermissions` (click-check 30), so the hook denies a write there. The hook is native. The check is not: a permission rule of a host (a Claude Code `deny` rule, a list of approved terminal commands) allows or stops a command always, and it does not know the approvals of a ticket. A native plan approval does not cover a push. So the hook asks Forge, and Forge answers from the manifests. The guard reads the words of the command (`git push`, `git -C`, `cd`, the branches that a push names, and the first words of the `repo.open-change` command of a trusted config). It does not see a script that pushes, so the written rules stay. It lets the command run when there is no ticket, no wiki, or an error. |
| The short session context, `context/tools.md`, and `tests/context-budget.test.mjs` | Plugin rule files do not load in each session (click-check 11), so the hook must carry the rules. No host has a rule file of a plugin that loads at a step, other than a skill. So the hook gives only the rules that apply before a skill loads: the paths, the ticket session rules, the "Never" list, the response style, and the verb rows of the host. The agent reads `context/tools.md` and the other parts of the host file at the step. The test keeps the sizes, because each rule that comes back makes each session longer. |
| `skills/ticket/phases/` and the size limit of `SKILL.md` | Resource files of a skill are native. The limit is a Forge rule: Claude Code keeps the first 5,000 tokens of a skill after a compaction ([Skills](https://code.claude.com/docs/en/skills), read on 2026-11-17), and the old `SKILL.md` had about 58,700 characters, so the phases from Start on were not in the context after a compaction. The VS Code docs do not say what a compaction keeps. `SKILL.md` now has the rules of each phase in at most 16,000 characters, and it tells the agent to read a phase file again after a compaction. |
| Behavioral evals: `tests/evals/` and `npm run eval` | `claude plugin eval` is the native runner of Claude Code ([Test plugins with evals](https://code.claude.com/docs/en/plugin-evals), read on 2026-11-17). Forge cannot use it yet, for 2 reasons. (1) Each shell command of a run is in the OS sandbox. On the development machine (NixOS, bubblewrap 0.12.0) each command fails with `bwrap: Can't mkdir parents for /run/secrets.d/2`, and a case with a "did not push" check then passes with and without the plugin.
